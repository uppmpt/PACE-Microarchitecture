# PACE Microarchitecture

**PACE** — *Pre-computing Antecipatory Core Engine* — is an RV64 in-order superscalar processor microarchitecture built around **scout-based pre-computation**. Written in pure Verilog (IEEE 1364, Verilog-2001) and simulated with Verilator.

## Overview

PACE separates *speculative pre-computation* from *commit-time execution*. Instead of predicting values, it **pre-computes them** in advance using dedicated scouts running at double the core clock. When the real execution reaches an instruction, the result is already available — or the AO-Cores take over transparently.

This design targets high IPC on branchy, arithmetic-heavy, and memory-intensive workloads while keeping the main pipeline in-order and simple to verify.

## Language & Tooling

- **Language:** pure Verilog (IEEE 1364, Verilog-2001). No SystemVerilog constructs.
- **Simulator:** Verilator
- **Target:** RV64 in-order superscalar core

## Architecture

### Core Pipeline

- **In-order superscalar** issue with decoupled functional units
- **Scout-based pre-computation** running at **2× core clock**
- **Modular interface** exposing inputs/outputs for extensions, caches, RAM, and Linux-capable peripherals

### Scouts (2× Clock)

Scouts pre-execute the instruction stream ahead of the main pipeline. They do not commit architectural state — they only produce *hints* (values, addresses, branch directions) stored for the real cores to consume.

| Scout | Role |
|-------|------|
| **PCU** — *Pre-computing Unit* | Pre-computes all integer and floating-point arithmetic using dedicated ALUs and FPUs |
| **M-Core** — *Memory Core* | Issues LOADs/STOREs, manages MSHRs and runahead, uses PCU to compute effective addresses |
| **B-Core** — *Branch Core* | Resolves all branches based on PCU results |

### AO-Cores — *Ahead Operations Cores*

The **AO-Cores** are the real execution cores. They consume results produced by the scouts and generate **architectural output**. If the PCU stalls, the AO-Cores continue executing independently until the PCU resumes — decoupling forward progress from scout availability.

### Shadow Register File

A **Shadow RF** holds scout-produced values. Besides operands, it stores **memory address tags** generated by LOAD instructions, increasing hit rate and reducing effective access latency for subsequent memory operations.

## Memory Subsystem

- **L1I / L1D / L2** — integrated in top-level (with MMU wrappers)
- **MESI coherence** — implemented as a standalone module; not yet integrated into the top-level core.
- **Sv39 MMU** — integrated (L1I/L1D MMU, TLB L1/L2, walker). CSR hookup (satp, priv_mode) partially complete.

## Extensions & Interfaces

The core is **modular by design** — all extension points are exposed as clean inputs/outputs:

- **Extension A** — atomic operations unit (partial support)
- **Extension V** — vector ALU, vector register file, vector CSRs (partial support)
- **Caches / RAM** — L1I, L1D, L2 integrated in top-level
- **Peripherals** — MMIO + interrupt interfaces for Linux-style peripherals. UART, CLINT, PLIC are provided as separate modules in pace_peripherals/ (not part of the core).

### Exposed Ports — Pluggable Consumers

Every external consumer connects through a well-defined port group. No module needs to be modified to add or swap a peripheral, cache, or extension.

| Consumer | Port Group |
|---|---|
| UART | mmio_* |
| PLIC | mmio_* + i_meip / i_seip |
| CLINT | mmio_* + i_mtip / i_msip |
| L1D / L1I / L2 | dmem_* / imem_* |
| A extension (atomic) | amo_ext_* |
| V extension (vector) | vmem_* |
| Runahead | rh_discard, rh_stall_*, rh_sb_full |
| MMU | Integrated (CSR-configurable) |
| MESI | Standalone module |

**Note on extension enablement:** The A (atomic) and V (vector)
extensions are implemented as separate modules, but they are **not
enabled by default** in the top-level core. To use them, the consumer
must make a **small modification to the core's top-level wiring** to
connect the extension ports and enable the corresponding CSR bits. See
the A and V extension modules for the exact port list.

## Verification & Testing

The design has been verified with a comprehensive testbench suite, located in the `pace_tb/` directory. Every major module and subsystem has at least one dedicated testbench, plus multiple integration tests covering cross-module behavior. All simulation is done with **Verilator**.

- **FPU**: tb_fpu_arith, tb_fpu_min, tb_fpu_dbg
- **Atomics (A)**: tb_amo, tb_amo_accept, tb_amo_exec, tb_amo_wrapper, tb_atomic
- **Vector (V)**: tb_vector, tb_vec_accept, tb_vec_mem, tb_vec_pcu
- **Pipeline & Cores**: tb_pcu, tb_pcu6, tb_pcu6_v, tb_pcu_bcore, tb_pcu_queue, tb_m_core, tb_b_core, tb_ao_core, tb_ao_multi
- **Register files**: tb_register_file, tb_shadow_rf, tb_shadow_rf_multi
- **Decoder / RVC**: tb_decoder, tb_rvc
- **CSR & Traps**: tb_csr_only, tb_csr_pcu, tb_csr_trap, tb_trap_imem, tb_trap_top
- **Boot**: tb_boot_seq, tb_boot_proto, tb_boot_final
- **Caches**: tb_l1i, tb_l1d, tb_l1d_mmio, tb_l2, tb_mc_l1d, tb_mesi
- **MMU / TLB / Sv39**: tb_mmu_min, tb_mmu_sv39, tb_mmu_top, tb_l1d_mmu, tb_sv39_walker, tb_tlb_l1, tb_tlb_l2

### Running the Tests

All tests are run with **Verilator**. To run the full suite, use the provided `run_all.sh` script from the project root:

```
bash run_all.sh
```

Individual tests can be run with Verilator directly. Example:

```
verilator --binary -j 0 -Wall pace_tb/tb_NAME.v pace_rtl/*.v
./obj_dir/Vtb_NAME
```

## Known Limitations

Please read this section carefully before using or evaluating the design.

- **Unit-level verification is complete.** Every RTL component — pipeline stages, PCU, M-Core, B-Core, AO-Cores, ALUs, FPUs, atomics, vector unit, caches, MMU, TLB, Sv39 walker, CSRs, traps, and peripherals — has been tested in isolation and passes its own dedicated testbench under Verilator.

- **Some integration testbenches currently fail.** A subset of the top-level and multi-module integration testbenches (for example, certain tb_top_* and tb_two_cores variants) do not pass out of the box. The cause is currently traced to **incorrect wiring / connection between modules at the integration level**, not to bugs in the modules themselves.

- **What this means in practice:** the RTL building blocks are correct and usable. If you are integrating PACE into your own SoC or testbench, you should expect to review and possibly adjust the top-level interconnect to match your environment.

- **What this does NOT mean:** it does not mean the components are broken. Each component has been individually verified, and behavior at the module boundary matches its specification.

These integration issues are actively being worked on. Contributions, reports, and fixes are welcome.

## Features Summary

- Pure Verilog (IEEE 1364, Verilog-2001)
- RV64 in-order superscalar core
- Scout-based pre-computation (PCU / M-Core / B-Core) at 2× clock
- AO-Cores for real execution with stall decoupling
- Shadow Register File with memory address tagging
- Atomic extension (A) — partial support
- Vector extension (V) — partial support
- Sv39 MMU (L1I/L1D MMU, TLB L1/L2, walker) — integrated, CSR hookup partial
- MESI cache coherence — standalone module, not yet integrated
- Runahead execution with MSHR tracking
- Performance counters
- Trap & CSR handling with boot sequencer
- Linux-capable peripherals (UART, CLINT, PLIC)
- 70+ testbenches covering unit and integration testing
